# Invitation and SAS threat model

**Assets:** device identity binding, local verification state, invitation bearer capability, contact metadata, session integrity, and user confidence in who is on the other side. **Adversaries:** a forwarded-link recipient, malicious relay or network operator, QR/link substituter, nearby camera observer, malicious contact, and a compromised or outdated client. This document adds to `docs/connectivity/threat-model.md`; it does not replace the existing crypto/relay model.

| Threat | Failure mode | Required control / evidence |
|---|---|---|
| QR or link replacement | Attacker substitutes their own unsigned four-field invitation and fingerprint; a scan looks valid. | Treat payload as a claim, bind observed public pre-key identity to the claimed fingerprint, keep contact unverified, require independent human comparison. Do not describe a valid QR as authenticated. |
| Capability leakage | Screenshot, clipboard sync, link preview, browser history, telemetry, or query-string conversion leaks room-control bearer value. | Fragment-only link; no capability in logs/analytics/errors; minimal share text and copy warnings; existing room deletion/revocation path. Review platform clipboard/deep-link behavior. |
| Replay or indefinite invitation | Room record has no creation-time absolute expiry; pre-key bundle TTL is seven days and can be renewed. An old link may remain useful. | Do not claim automatic invitation expiry. Future explicit expiry/one-time semantics require backend/protocol review; until then use revocation and distinct unavailable errors. Test stale route vs deleted room. |
| SAS from unbound public material | Attacker computes or substitutes matching code without sharing the intended authenticated session. | Bind both identities, room, roles, fresh contributions, and authenticated key/session context; security-review exact transcript and confirmation exchange. No SAS from QR bytes alone. |
| SAS grinding or chosen-contribution attack | Attacker repeatedly chooses identities/nonces until a short code matches. | Reviewed active-attack bit target, role ordering, contribution commitments or equivalent anti-adaptation, attempt limits, timeout, no silent restart. Do not ship a six-digit code by default. |
| Comparison over compromised channel | Attacker relays or changes the code in the same untrusted chat used to establish contact. | Tell users to compare in person or over an independently authenticated channel. Same-chat comparison is not verification. |
| Peer or relay auto-confirms | Remote signal, relay ACK, QR scan, or contact creation flips local trust. | Only explicit local user confirmation invokes existing trust upgrade. Server and transport have no trust-write authority. Test every state transition. |
| Stale/concurrent ceremony | Old code survives reconnect, session reset, identity change, device revocation, or two parallel attempts. | Fresh context, single active ceremony, expiry and cancellation; invalidate on binding/trust lifecycle changes; reject replayed confirmations. |
| Identity change hidden by nickname or route | Old verified label attaches to new key, route, or device. | Compare immutable identity binding, preserve changed-pending-review state, require fresh explicit verification; names and routes never prove identity. Android trust-label parity is a prerequisite. |
| Mixed client versions | New control frame is sent to a strict old decoder or SAS is presented without mutual support. | Capability negotiation per ADR 0008; default to existing fingerprint workflow, without upgrading trust or changing session state. Test Web/Android/old-client combinations. |
| Malformed QR/deep link | Oversized, duplicate, unknown, mixed-origin or ambiguous fields trigger parsing differences or exfiltration. | Exact-field strict parsers, size bounds, explicit wrapper version if ever added, app-origin validation, cross-platform fixtures and fuzz tests. |

**Privacy note:** even a public identity fingerprint can correlate a device across contexts. Do not put stable fingerprint, profile name, contact list, or SAS in discovery adverts or analytics. The current invitation necessarily contains the inviter's fingerprint and route; communicate that disclosure honestly.

**Security review gates:** exact SAS construction/transcript; capability exchange and old-client behavior; Android trust-state parity; QR/deep-link exposure; invitation lifetime policy. A failure at any gate retains fingerprint verification and the current beta flow.
