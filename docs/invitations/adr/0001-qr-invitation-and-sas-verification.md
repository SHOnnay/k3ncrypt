# ADR 0001: QR invitation and SAS verification ceremony

**Status:** Proposed; specification only. Security review is required before any SAS wire format or trust-state change.

## Context and evidence

The current modern invitation is a URL fragment with exactly four fields: `modern` (room UUID), `control` (43-character bearer control capability), `address` (inviter's published pre-key route UUID), and `identity` (inviter's `K3` device fingerprint). Web creates the full same-origin URL in `client/src/context/ChatContext.tsx`; Android creates the fragment in `MainActivity.kt`. Both parsers require the same field set and reject duplicates. QR and share actions carry these existing bytes; QR is a carrier, not a separate authorization protocol.

The fragment is **not signed**. The inviter's `identity` is a claimed commitment that the joiner checks against the fetched public pre-key bundle. A person who replaces the whole invitation can substitute their own room, capability, route, and identity; neither a parse success nor a successful network join proves the human sender. The room record stores only a hash of `control`, while the fragment contains the bearer value. The room record has `expired`/`deleted` flags, but creation does not assign an absolute invitation expiry. Published pre-key bundles have a seven-day TTL and may be renewed. These are different lifetimes; a stale route is not proof that a room or invitation expired. No one-time redemption or invitation-use limit is evidenced by the current four-field format.

Current Web trust is a local `contact-identity` record: observing a peer records `unverified`; `verifyContact(true)` calls `markVerified` after an explicit comparison; identity change drops active verification and requires review. Web also has a *separate*, public-only verification QR containing a fingerprint. Android pins the fingerprint provided at join, checks the fetched pre-key identity, and requires the user to re-enter it before joining; it also asks the inviter to confirm a first observed peer. Its saved-conversation summary currently derives `isTrusted` from non-empty peer route and fingerprint, rather than from an equivalent persisted Web verification flag. Neither an Android re-entry nor a matching QR image alone authenticates the human source.

## Decision

1. Keep the existing modern invitation format and relay/Olm behavior for the beta. A future **versioned QR presentation wrapper** may identify the same underlying invitation and its intended app link, but it must not silently change the four-field protocol, add trust claims, or include private keys, profile names, SAS values, or device inventory. The minimal first release should render and scan the existing fragment/full link with strict parsing.
2. The contact state after a valid join is **created, unverified**. On the inviter, this state waits for an authenticated introduction carrying the joiner's identity descriptor; a route or room shell alone is insufficient to start verification. Joining and contact creation must never call a trust upgrade.
3. A future SAS is a **new verification ceremony**, not a replacement for the existing fingerprint or its generation. It is shown only after both sides possess a validated, stable peer identity and an authenticated, current conversation/session binding. Both people compare the *same ceremony* over an independent trusted channel or in person, then each explicitly confirms locally. One person's confirmation does not confirm for the other.
4. A SAS must be derived from a fresh, role-ordered, domain-separated transcript binding protocol/ceremony version, room identity, both complete device identity fingerprints or authenticated public identities, both roles, both fresh contributions, and the current authenticated key/session or key-confirmation context. Canonical byte encoding and shared Web/Android vectors are mandatory. The displayed value must have a reviewed active-attack work factor, including repeated-attempt and precomputation analysis; a short unbound six-digit code is not accepted by this ADR. How the fresh contributions are committed/exchanged and the exact digest/encoding are **open cryptographic design decisions**, not authorized implementation details.
5. A ceremony must expire, be single-use per transcript, and be invalidated by identity change, session replacement, device trust/revocation change, conversation change, cancellation, or conflicting concurrent ceremony. No cached SAS is evidence of current trust. A mismatch leaves the contact unverified and offers fingerprint comparison or restart; it never accepts automatically.
6. Trust persistence remains device-local under the existing secure-storage authority. A reviewed implementation may record the comparison method and ceremony version as local audit metadata, but only the existing explicit trust upgrade path may change verification state. Android's route-plus-fingerprint summary must not be interpreted as completed SAS verification; reconciling its trust presentation/storage is a separate reviewed prerequisite.
7. Mixed versions use the current fingerprint comparison. Do not send a new control frame to an old peer. Capability negotiation for any future SAS exchange must satisfy `docs/connectivity/adr/0008-capability-negotiation.md`; peer-advertised relay metadata alone is insufficient. No SAS support means **unverified**, never automatic fallback to a weaker trust assertion.

## QR and link requirements

- Treat the fragment as a bearer secret. Keep it in the URL fragment only; never place it in a query, analytics, logs, crash reports, link previews, or unrelated share text. QR screenshots and shared links can still leak it; warn the sender and allow room revocation using existing controls.
- Accept only the existing exact four fields during the compatibility phase, with one occurrence each and bounded lengths. If a wrapper is later approved, version it explicitly, bind an allowed app origin, reject unknown or duplicate fields, and pass its inner invitation to the existing strict parser. A wrapper is a transport container, not a signature.
- A normal HTTPS link remains usable when app deep-link handling is unavailable. Android app-link ownership and browser fallback require platform validation; do not let an arbitrary third-party host become an authority for the claimed identity. Confirm before switching from a browser to an app, and do not send the fragment to the server.
- Display availability accurately: a missing/deleted room, expired pre-key route, and transient service failure are distinct. Do not promise a time-to-expiry until the backend actually enforces one. Copy/share/scan must transfer the identical invitation fields on Web and Android.

## Consequences and gates

This ADR defines the product/security boundary, not a protocol. The user-facing target is `QR invitation → unverified contact → SAS or legacy fingerprint comparison → locally verified contact`. The exact SAS construction, freshness/commitment exchange, Android trust parity, and any new capability or QR wrapper need a separate security-reviewed ADR, fixtures, migration plan, and mixed-version tests before implementation. Existing beta clients and existing conversations continue to use fingerprint verification unchanged.

See [UX flow](../ux-flow.md), [threat model](../threat-model.md), and [implementation plan](../implementation-plan.md).

The follow-up [verification ceremony design](../verification-ceremony-design.md) recommends an interactive, identity-bound SAS over the authenticated conversation, with the invitation QR remaining contact setup only. It records the current Web/Android implementation audit, compatibility behavior, security requirements, phases, test matrix, and unresolved cryptographic decisions. The protocol remains unapproved for implementation until those decisions receive separate security review.
