Base commit: `fd39808abf554e8f0aed58962e898e6870b1878e`.

## Gate result

The initial stop-report findings were confirmed against the source. This
checkpoint implements a reviewable, versioned attachment AEAD/context contract
for Web and Android and closes the recipient/owner authorization gaps for
recipient-bound transfers. The original five security acceptance gates now
pass. The full transfer product is still stopped at this human-review point:
there is no new picker, download UI, streaming, resume, or durable transfer
lifecycle.

The new v2 adapter is a separate security foundation API. Existing v1 media
upload references are not silently reinterpreted as v2. V1 receive now
authenticates and validates its encrypted metadata before returning plaintext.
Legacy server records with no recipient binding retain the old conversation
member read rule for compatibility; new secure transfers must include the
recipient participant and pinned identity reference.

## Crypto and wire contract

- Primitive: platform/WebCrypto AES-256-GCM; no custom cipher, key derivation,
  or authentication construction.
- Android: `AttachmentAead` uses JCA `AES/GCM/NoPadding` with the caller's raw
  per-transfer file key. It is in `android/media`, separate from local storage.
  The `android/storage` Keystore key and adapter are unchanged.
- Web: `portableAead.ts` uses WebCrypto AES-GCM. The existing v1
  `decryptAttachment` additionally calls `decryptAttachmentMetadata` before
  releasing any bytes and rejects unbound context fields.
- Key: 32 bytes (AES-256). Nonce/IV: 12 bytes, generated by WebCrypto
  `getRandomValues` or Android `SecureRandom`. Tag: 16 bytes (128 bits),
  appended to ciphertext. Both adapters use this exact `ciphertext || tag`
  layout. Authentication/context failures are fail-closed.
- Nonce lifecycle: each manifest/chunk encryption call generates a fresh
  random nonce under the per-transfer key. At most 257 objects are allowed per
  transfer, making random collision probability negligible for this object
  bound. A retry must resend the exact persisted `(nonce, ciphertext || tag)`;
  callers must never encrypt different plaintext again under a prior nonce.
  Durable retry/resume is not implemented here. Future persistence must retain
  the exact sealed object and nonce together before upload; resumed transfers
  must reuse it, not reseal it.
- AAD v2 bytes, in order: ASCII `k3ncrypt/attachment-aad/v2\0`, version u8
  (`2`), object type u8 (`1` manifest, `2` chunk), four UUIDs as 16 raw bytes
  (transfer, conversation, sender participant, recipient participant), sender
  pinned identity reference as u16 byte length + UTF-8, recipient pinned
  identity reference in the same form, file size u64 BE, chunk size u32 BE,
  chunk count u32 BE, chunk index u32 BE (`0xffffffff` for manifest). Integer
  widths and big-endian ordering are explicit. Both participants must be
  distinct, both stable identity references must match K3NCRYPT's canonical
  pinned fingerprint syntax, and chunk/count/size bounds are checked.
- Binding decision: use stable conversation authority plus the sender and
  intended recipient's pinned identity fingerprints. Do not bind to ephemeral
  Olm session IDs: that would strand legitimate transfers on session renewal.
  The authenticated conversation message remains responsible for conveying
  the file key/reference end to end.
- Manifest v2 plaintext is binary and canonical: ASCII
  `k3ncrypt/manifest/v2\0`, u64 size, u32 chunk size/count, u64 creation and
  expiry milliseconds, then u16-length strict UTF-8 normalized filename and
  MIME. The encrypted/authenticated manifest covers filename, MIME, size,
  chunk geometry and timestamps. Server-visible routing/storage fields remain
  separate and do not replace authenticated context. A manifest is opened and
  validated before its fields are trusted; chunk/manifest substitution and
  context mutation fail authentication.
- Chunk v2 is AES-GCM authenticated with the same context and its own chunk
  index. Expected plaintext length is checked per index. Tag, ciphertext,
  nonce, context, and object-type mutations fail closed.

## Identity, keys, and authorization

- Existing Web `generateAttachmentKey` generates a random 32-byte attachment
  key. Existing media messaging places the reference/key inside the normal
  encrypted conversation message; the receiver gets it only after normal
  E2EE message decryption. This task adds no key exchange and changes no Olm
  identity/session crypto.
- The adapters do not retain or persist the supplied key. The active caller
  owns its in-memory lifetime and must clear its key buffer on completion or
  cancellation. No raw key, plaintext manifest, nonce/ciphertext diagnostic,
  or media bytes are logged. Resume is out of scope; if later implemented, the
  key may only be persisted through existing encrypted E2EE/local protected
  state, never in clear server metadata.
- Production attachment authentication now verifies the device proof's
  `deviceIdentityReference` against the current published participant bundle
  fingerprint before creating `AuthenticatedContext`. The backend checks the
  sender is an authenticated room member, the recipient is a room member, and
  the recipient's requested pinned identity equals its server-published
  identity. Transfer access metadata records conversation, owner, recipient,
  and both identity references.
- The AAD codec validates fingerprint syntax, but does not itself decide
  whether a peer is verified. A future sender flow must source the intended
  recipient fingerprint from the existing verified-and-unchanged contact
  authority before encrypting/sending the E2EE reference. The backend's live
  publication match prevents stale/replaced identities from inheriting an old
  record; this foundation adds no new client-side verification flow.
- Sender-only write/delete are enforced. Reads on recipient-bound records are
  limited to the exact recipient participant and pinned identity. Room
  membership, transfer UUID, and attachment capability alone do not establish
  the intended recipient role. Identity replacement does not inherit an old
  transfer: current authenticated identity must equal the recorded fingerprint.
- Completion requests now map to the existing attachment-write device-trust
  operation. Existing local Keystore behavior is unchanged.

## Interoperability evidence

`protocol-fixtures/v1/attachment-aead-v2.properties` is a fixed, public,
test-only vector. Both WebCrypto and Java/JCA consume the same key, context,
manifest bytes, chunk bytes, nonces, and expected ciphertext/tag. Each adapter
reproduces the exact expected ciphertext and decrypts the same expected
ciphertext. This proves wire compatibility for the established APIs; it is
not a physical-device test of every Android provider or a full user-flow test.

The shared negative matrix checks transfer, conversation, sender participant,
recipient participant, sender identity, recipient identity, type, chunk index,
size/chunk geometry, nonce, ciphertext, tag, and manifest/chunk substitution.
Separate security tests verify the original manifest and participant gates,
positive intended-recipient read, wrong-recipient identity at creation,
identity replacement, cross-conversation access, non-recipient room publisher,
and owner-only write/delete.

## Scope and remaining risks

- The v2 crypto contract is not yet wired into a complete upload/download
  product flow. Existing v1 media remains on its original wire format.
- Existing legacy unbound attachment records continue to use the previous
  conversation-member read behavior. New secure transfer creation must require
  recipient binding; the follow-on integration must not use the legacy path.
- Durable nonce persistence/retry, sender/receiver resume, storage quotas,
  large-file streaming, key-buffer erasure orchestration, Android device
  provider verification, and physical Web/Android file interop remain future
  work and must be designed/tested before shipping the full feature.
- No changes were made to video/call code, Local Session, the video test
  branch, `integration/main-product`, or the preserved stash.
